# AGENTS.md

Файл для агентов и для людей, которые подхватывают работу в этом репозитории. Держим его
единственным источником «состояния проекта»: если меняется архитектура, порядок проверки или
известные ограничения — правится в первую очередь этот файл, потом `README.md`.

Конкретику проекта не дублируем: константы, цвета, кегли, размеры и количества живут в коде, CSS и
конфигах. Здесь — решения, причины и грабли, а не значения: они стареют молча и мешают править.

## Как работать с задачами

Это MVP, а не ракета в космос. Договорённость с владельцем репозитория:

- Простая задача — простое и быстрое решение, даже в ущерб качеству. Не наращивать объём работы.
- Дополнительные проверки (полный прогон проекта, пробники, сборка, headless-браузер) — только когда
  задача этого реально требует; если можно не проверять — не проверять, владелец проверит сам и скажет.
- Прогоны вроде `npm run lint` / `check-types` / `build` не запускать «на всякий случай»: они нужны
  перед коммитом или когда правка реально может их сломать.
- Не расширять задачу самовольно: спросили одно — делаем одно.
- Задачу не коммитить: коммит — только по прямой просьбе владельца. Правки владельца в рабочем дереве
  не откатывать и не затирать: раз что-то добавлено или удалено — так и надо.
- Проверки соразмерны правке: поправил данные или `AGENTS.md` — перепроверять нечего; `check-types` нужен,
  когда правка в коде и правда может его сломать, а `lint` дёрнется на пре-коммите.
- Если правило линтера мешает и код приходится уродовать в обход — спросить владельца, можно ли правило
  отключить; отключённое правило фиксируется в `.eslintrc.cjs`.

## Что это за проект

Учебная визуализация графа: React 19 + TypeScript + Vite, физика и работа с DOM — на d3
(`d3-force`, `d3-selection`, `d3-drag`, `d3-zoom`, `d3-scale-chromatic`), форма настроек — на
`react-hook-form`.

`src/App.tsx` — каркас страницы (хедер «Карта», пустой футер, `aside` слева и карта в `main`).
В `aside` лежит панель настроек (`SettingsPanel`), карта — компонент `ForceGraph` (научные работы и
цитирующие их патенты; исторически проект вырос из примера d3 про несвязный граф, но мы от него
уходим, и сверяться с ним больше не нужно). Данные лежат TS-модулем в `src/data/graph.ts`, типы — в
`src/types/graph.ts`; запроса к серверу нет, состояние загрузки эмулируется `setTimeout`.

Раскладка сайта и сцены — в CSS (`src/App.css`, `ForceGraph.css`, `src/index.css`): каркас на всю
высоту экрана, у секций фоны-различители, шрифт системный.

## Команды

- `npm run dev` — дев-сервер Vite (`npm run dev -- --port 5199 --strictPort` фиксирует порт).
- `npm run build` — `tsc -b` + продакшн-сборка в `dist`.
- `npm run preview` — просмотр собранного `dist` (`--port 5198 --strictPort` при проверках).
- `npm run check-types` — только типы (`tsc -b`, инкрементально через `.tsbuildinfo`).
- `npm run lint` — prettier `--write` по всему проекту + eslint `--fix`.
- `npm run lint-all` — то же, что `lint-es` (алиас).
- Пре-коммит хук `.git-hooks/pre-commit` запускает `npm run lint` и отменяет коммит при ошибке;
  путь подключается скриптом `prepare` при `npm install`.

## Структура

- `src/App.tsx` — каркас страницы: хедер с заголовком «Карта», слева `aside` с панелью настроек,
  справа `main` с картой, снизу пустой `footer`. Настройки живут в стейте `App`: панель их меняет,
  карта получает их пропом.
- `src/App.css` — раскладка каркаса: колонка на всю высоту экрана, тело `flex: 1` отдаётся
  паре `aside` + `main`, у секций светлые фоны-различители.
- `src/index.css` — глобальные стили: `normalize.css` первым `@import` и системный шрифт.
- Компоненты экспортируются именованно (`export function App`, `export function ForceGraph`), без
  default-экспорта: импорты тогда всегда `{ … } from './…'`.
- Комментарии не должны пересказывать код: тип поля, имя функции или константы уже говорят «что»
  делается. Комментарий нужен про «почему» — обоснование значения, следствие замера, ограничение,
  которое иначе нарушат.
- `src/components/SettingsPanel/SettingsPanel.tsx` — панель настроек с заголовком «Настройки»:
  форма на `react-hook-form` (селект числа клонов нод, тоггл полного вида саб нод, чекбокс скрытия
  саб нод, range-поля физики, кнопки «Применить»/«Сбросить»). Сабмит сохраняет значения и отдаёт их
  в `App`, сброс возвращает форму к значениям по умолчанию. Поля физики рисуются списком
  `NUMBER_FIELDS` (не вручную): состав, пределы и подписи лежат в `settingsPanel.ts`. У каждого
  нового поля `title` с коротким пояснением — что ручка меняет на карте.
- `src/components/SettingsPanel/settingsPanel.ts` — логика панели без React: значения по умолчанию,
  допустимые числа клонов, описание числовых полей (`NUMBER_FIELDS`), ключ и чтение/запись
  localStorage. Дефолты физики импортируются из `forceGraph.ts`, а не переписаны здесь: панель и
  сцена не должны разойтись, когда значение подгоняют по картинке. Разбор строки из хранилища —
  чистая функция `parseGraphSettings`, проверяется в Node.
- `src/components/SettingsPanel/SettingsPanel.css` — вид панели (классы `settings-panel__*`): поля,
  тоггл и чекбокс нарисованы подменными элементами поверх настоящих чекбоксов, палитра как у сайта.
- `src/components/ForceGraph/forceGraph.ts` — чистая логика без DOM: константы сцены, `prepareGraph`,
  `createSimulation`, `createLinkForce`, `asDrawnLinks`, `createTypeColors`, `tintToWhite`, типы
  `NodeRenderData`/`SeedPoint`/`GraphPhysics`. Константы посева (`NEW_NODE_SEED_*`) и разогрева
  (`UPDATE_ALPHA`) — здесь. `GraphPhysics` — необязательные переопределения поведения карты
  (`layoutScale`, `linkDistance`, `linkStrength`, `chargeStrength`, `velocityDecay`,
  `dragAlphaTarget`, `updateAlpha`): силы читают их через `??`, поэтому отсутствие поля означает
  прежнюю константу, а не ноль.
- `src/components/ForceGraph/forceGraphUpdate.ts` — сведение CRUD-операций в план обновления:
  `readGraphState` (текущее состояние читается из симуляции и силы связей, отдельного «прежнего
  графа» нет), `diffNodes`, `planGraphUpdate` (что добавить/изменить/удалить и где встать новым) и
  `applyGraphUpdate` (следующие списки для сил и для отрисовки плюс ключи перерисовки). Модуль
  чистый, без DOM и без симуляции — весь разбор проверяется в Node.
- `src/components/ForceGraph/crud/graphNodesCRUD.ts` — CRUD узла: ключ (`nodeKey`), снимок
  отрисовываемых значений (`nodeRenderData`), сравнение (`isNodeRenderDataChanged`) и сборка объекта
  узла для симуляции (`buildNode` + `seedPosition`). Тоже чистый.
- `src/components/ForceGraph/crud/graphLinksCRUD.ts` — CRUD связи: направленный ключ (`linkKey`,
  `linkKeyOf`), разбор новых связей относительно прежних (`diffLinks`: добавление/оставление,
  отбрасывание связи с несуществующим концом и дубликата), посев новых узлов (`collectSeeds`) и
  сборка объекта связи (`buildLink`). Тоже чистый.
- `src/components/ForceGraph/forceGraphCloud.ts` — геометрия узлов, тоже без DOM: кегли и паддинги
  текста, `truncateToWidth` и `createCloudLayouts(nodes, measure)`. Мерку текста получает
  аргументом (`MeasureText`), поэтому проверяется в Node с фейковой меркой.
- `src/components/ForceGraph/forceGraphText.ts` — `createTextMeasurer()`: offscreen-канва для
  `measureText`. Единственное место, где ширина строки берётся у браузера.
- `src/components/ForceGraph/layers/graphLayer.ts` — базовый svg-слой: `Map<ключ → элемент>` и
  `sync(data, dirtyKeys)` с enter/update/exit: проход по предыдущему состоянию слоя, новые элементы
  добавляются, лишние снимаются, а перерисовка (`renderer.update`) дописывается только элементам из
  `dirtyKeys`. Не знает ни про узлы, ни про связи — только про «набор однотипных элементов с
  ключом». Снятый элемент очищается от `__data__` (`forgetElement`).
- `src/components/ForceGraph/layers/graphLinkLayer.ts` — слой связей (`LinkLayer`): по `<line>`
  на связь, толщина `√force`, `drawPositions()` переносит координаты концов.
- `src/components/ForceGraph/layers/graphNodeLayer.ts` — слой узлов (`NodeLayer`): группа с
  фиксированным составом детей (подсказка, тело, заголовок, описание, точка предупреждения, точка
  иконки) и ссылками на них в записи слоя, поэтому обновление пишет атрибуты без поиска по DOM.
  Вид узла сворачивается в `renderKey`; совпал — группу не трогаем (раскладка и мерка текста не
  вызываются). Перерисовка приходит только на ключи из `dirtyKeys`, которые выдаёт план обновления.
- `src/components/ForceGraph/forceGraphView.ts` — сборка svg и порядок применения обновления:
  панорама/зум, drag, tick-отрисовка слоёв, `update(data)`, `setPhysics(physics)` и `destroy()`.
  Единственный модуль, который создаёт DOM-сцену. Значения физики лежат в одном объекте замыкания,
  который читают силы и drag-хендлер: `setPhysics` переписывает его, отдаёт новые параметры
  `forceLink`/`forceManyBody`/`velocityDecay` и разогревает симуляцию — сцена при этом не
  пересобирается, поэтому вид панорамы и накопленная раскладка сохраняются.
- `src/components/ForceGraph/ForceGraph.tsx` — React-обёртка: эмуляция загрузки на `setTimeout`,
  клонирование графа по настройке `nodeClones` (`useMemo`) и монтирование svg в контейнер. React
  владеет только контейнером, svg императивный. Сцена создаётся один раз — на первых данных, все
  последующие изменения доставляются на месте: правки данных и клонирование через `handle.update(data)`,
  значения физики через `handle.setPhysics(physics)` (см. «Инкрементальное обновление сцены»).
  Разрушение сцены — отдельный эффект без зависимостей; в cleanup эффекта создания оно давать
  нельзя: React запускает cleanup перед каждым повторным прогоном, так что смена любой зависимости
  пересобирала бы svg и весь инкрементальный разбор шёл бы насмарку.
- `src/components/ForceGraph/ForceGraph.css` — раскладка фигуры и сцены (классы `force-graph__*`):
  фигура растягивается на `main`, а svg заполняет фигуру, пропорции держит viewBox.
- `src/data/graph.ts` — данные графа одним типизированным модулем (`graphData`), импортируются
  напрямую, без `fetch`. Файл сгенерированный и очень длинный, поэтому `max-lines` для `src/data`
  отключён оверрайдом в `.eslintrc.cjs`. Связи здесь перепакованы искусственно (см. «Правила работы
  с графом»), а идентификаторы патентов идут с пропусками: удалённые патенты своих номеров не отдают,
  и по `patent-N` всё ещё видно, откуда узел родом.
- `src/types/graph.ts` — типы данных: `GraphNodeType`, `GraphNodeInput`, `GraphLinkInput`,
  `GraphData` и типы уровня симуляции (`GraphNode`, `GraphLink`, `DrawnLink`).
- `src/types/settings.ts` — `GraphSettings`: настройки, которые собирает панель (число клонов нод,
  полный вид саб нод, скрытие саб нод и семь числовых ручек физики). Числовые поля здесь не
  опциональные: панель обязана привезти значения, а `GraphPhysics` в сцене — опциональный, чтобы
  вызывающий мог передать только то, что крутит.

## Конвенции кода

Зафиксированы `.prettierrc.mjs`, `.eslintrc.cjs` и текущим кодом — не менять по вкусу:

- Форматирование — по `.prettierrc.mjs` (табы, без точек с запятой, одинарные кавычки и т. п.);
  стиль не править по вкусу, за него отвечает пре-коммит.
- Комментарии, JSDoc и тексты интерфейса — по-русски. JSDoc на каждом экспорте.
- `import type` для типов (`verbatimModuleSyntax`), порядок импортов поддерживает
  `prettier-plugin-organize-imports` на пре-коммите.
- Объявлять функции до использования: базовый `no-use-before-define` отключён, но
  `@typescript-eslint/no-use-before-define` из airbnb — ошибка.
- Не мутировать параметры обработчиков (`no-param-reassign`): в drag-хендлерах предмет жеста
  берётся в локальную переменную (`const { subject } = event`).
- У линтера есть лимиты на длину файла и функции (значения — в `.eslintrc.cjs`): при упоре делить
  модуль по ответственности, а не ужимать код. Для `src/data` лимит строк погашен оверрайдом — там
  данные, а не логика.
- Логика отделяется от отрисовки: физику, данные и раскладку облаков тестируем в Node (без DOM),
  svg собирается только в `forceGraphView.ts`.
- Типам d3 нужны явные дженерики, иначе получаются union-типы: `selectAll<SVGLineElement, DrawnLink>('line')`,
  `drag<SVGGElement, GraphNode, GraphNode>()` (третий параметр — subject), а итерация по узлам — через
  `each((datum, index) => …)` + `select(node.nodes()[index])`: селекционный выбор данных в `each` не приходит.
- Намеренно неиспользуемый параметр/проп переименовывается с подчёркиванием (`settings: _settings`):
  при `noUnusedLocals` иначе `tsc` ругается TS6133, а отключать правило ради пары мест не стоит.

## Правила работы с графом

- Силы подогнаны под крупные облака: `forceLink` + `forceManyBody` +
  `forceX`/`forceY`. Заряд масштабируется как площадь, а дистанция связи задаётся отдельно и короче
  этой растяжки — связанные узлы должны стоять плотнее тех, что просто отталкиваются. Это две
  независимые ручки: дистанция связи отвечает за плотность связок внутри кластера, заряд — за простор
  между узлами. Подгоняются по картинке, и после перепаковки данных связку укоротили: кластеров стало
  больше, и с короткой связью они читаются сгустками, а простор между ними остаётся. Позиционирующие
  силы линейны и остаются как есть — они же принципиальны: у графа много несвязных компонент, и
  `forceCenter` разносит их за пределы сцены. Масштаб сцены и зума при растяжке не менялся: карта
  рассчитана на панораму. Жёсткость связки задана явно и слабо (`LINK_STRENGTH` — плоское значение
  для всех связей): формула d3 (`1 / min(степеней концов)`) листовым связям отдавала полную
  силу 1, и лист степени 1 держал партнёра крепче всех. Замер: ослаблять связку ниже типичного для d3
  значения не надо — связки расползаются, раскладка уходит от равновесия и качается сильнее, то есть
  «желе» так не лечится. Заряд между несвязанными узлами тоже не ручка «желе», хотя влияние на карту
  оказывает именно он: снижение `|CHARGE_STRENGTH|` и обрезка его радиуса (`distanceMax`) сжимают
  сцену — тела начинают налезать (наезды 8 → 15…42 при 25 у сниженного заряда), а прокат от жеста
  остаётся прежним или растёт. Простор между облаками держится зарядом, поэтому его не трогаем.
- Узлы держатся «статично», а не как желе: демпфирование скорости выше дефолта d3, а drag разогревает
  симуляцию слабо (`alphaTarget` — `DRAG_ALPHA_TARGET`, `fx`/`fy` в точке узла, сброс в `null` и
  `alphaTarget(0)` на отпускании). Так узел идёт за курсором, соседи подтягиваются, а остальная карта
  почти стоит; числа в коде. Главная ручка «желе» — именно разогрев жеста: замер показал, что снижение
  вдвое (0.1 → 0.05) вдвое уменьшает и прокат остальных узлов, и остаточный сдвиг карты после жеста,
  тогда как ослабление связки на тот же порядок даёт обратный эффект. Ниже 0.05 соседи за курсором уже
  не поспевают, и демпфирование выше текущего тоже вредит: движение уходит в фазу остывания, а
  раскладка садится в другое равновесие.
- `link.force` — необязательная сила связи (как крепко концы держатся друг за друга): физика её пока не
  читает, поле хранится на будущее, а сейчас из неё считается только толщина линии. Неиспользуемые
  поля исходных данных в проект не переносились.
- Данные — не буквальный граф цитирований, а его форма для раскладки: 100 работ остались исходными,
  а патентов оставлено 112 из 236, и часть их связей переназначена на другие работы. Так лечились две
  болезни исходных данных: россыпь компонент из двух узлов (работа + патент) и «звёзды» — одна работа
  с десятком патентов. Правила перепаковки: несвязная компонента — либо сохранённая пара работы
  с патентом, либо кластер из 3–8 узлов (2–6 работ + 1–6 патентов); сохранённых пар 11 (примерно
  треть исходных); патенты-связки внутри кластера держат по две-три работы, остальные висят листьями;
  бывшие хабы остаются узлами с несколькими связками, но в кластере не крупнее 8 узлов. Часть
  патентов сохранена как есть вместе со своими работами: там, где исходная компонента уже укладывалась
  в норму, ничего не переписывалось. Перепаковка разовая и живёт в истории — в `src/data/graph.ts`
  лежит уже готовый результат, отдельного генератора в проекте нет.
- Кластеры заданы данными, а не физикой: силы сцены про них не знают и специально под них не
  подгонялись. Если карта снова покажется разрозненной, сначала смотреть на форму данных, а не
  крутить `LAYOUT_SCALE`/`LINK_DISTANCE`. Обратное тоже верно: плотность связок и простор между
  узлами — это подгонка по картинке, и в кластеры она узлы не собирает.
- Константы физики остаются источником дефолтов, но теперь их можно переопределить из панели
  (`GraphPhysics`): крутить ручки допускается прямо в браузере, а в код значение переезжает только
  если оно подтверждено как новое постоянное — вместе с обоснованием замера. Правильные значения
  живут у константы, а не в localStorage: хранилище отдаёт старые настройки целиком, если поля не
  сошлись (см. `parseGraphSettings`).
- Цвет — по `type` узла, как аналог `scaleOrdinal(schemeCategory10)`: оттенки выдаются в порядке
  первого появления типа, поэтому легенда не нужна. Типов два: `node` — научные работы, `subNode` —
  цитирующие их патенты; палитра та же, что была у групп `Cited Works`/`Citing Patents`.
- Тела узлов — скруглённые прямоугольники центрами на координатах узла; группу двигает один
  `transform: translate(x,y)`, поэтому внутри всё считается от нуля. Заливка — не прозрачная, а светлый
  оттенок цвета типа (`tintToWhite`, доля белого — `BODY_FILL_WHITE`), поэтому связи под облаком не
  просвечивают, а оттенок типа остаётся. Обводка — тот же цвет в полную силу. `node` — «облако» по
  размеру текста: строки по левому краю, блок строк центрирован по вертикали, длинные строки обрезаются
  с «…». `subNode` — почти круг с яркой точкой в центре; данных у иконки на сцене нет. Кегли, паддинги,
  скругления и потолок ширины — в `forceGraphCloud.ts`.
- Текст мерит offscreen-канва той же гарнитурой (`FONT_FAMILY`, как системный шрифт в `src/index.css`),
  которой он потом рисуется: так `measureText` не расходится с отрисовкой. Семейство задаётся и на
  группе узла, потому что атрибут не наследуется в канву.
- Короткие подписи работ — русские и авторские, а не перевод исходных названий: это подписи на карте
  рядом с облаком, полное название не теряется — оно в `description`. Так и оставляем.
- `type` — только два значения, третьего не будет: данные `subNode` (`title`, `description`) не чистим,
  контент понадобится, когда иконка начнёт раскрываться.
- `hasWarning` — данные под красную точку в левом верхнем углу облака: слева резервируется колонка
  `WARNING_GUTTER`, текст сдвигается правее. Сейчас у всех узлов `false`.
- Узел несёт короткий `title` (у работы — сокращённая подпись, у патента — номер) и необязательный
  `description`: у работы там полное название статьи, у патента его нет. В нативной подсказке
  (`<title>`) видно и то и другое, строки склеивает `nodeTooltip`; на карте при этом обрезанные
  подписи, полный текст остаётся в подсказке.
- Панорама/зум — добавка к базовой раскладке; сетка фона удалена целиком вместе с
  модулем. Узлы жест панорамы не перехватывают (d3-drag глушит всплытие).
- Клонирование нод (`nodeClones` в настройках) клонирует граф целиком, а не размер узлов: каждая
  копия получает id с префиксом `N-` и свои связи, подписи копий совпадают с оригиналом. Это ручка
  «посмотреть на много компонент», а не масштабирование; множителя размера узлов в проекте не будет.
- Данных с сервера нет и не будет: `ForceGraph` импортирует `graphData` из `src/data/graph.ts`, поэтому
  состояние «Загрузка графа…» — чистая эмуляция. Данные меняются в стейте и доставляются в уже собранную
  сцену через `handle.update(data)`: узлы и связи добавляются, обновляются и удаляются, а раскладка,
  панорама и симуляция сохраняются. Если данные когда-нибудь вернутся в запрос, `resolveJsonModule`
  в `tsconfig` не включён — импорт JSON не «просто заработает». Механизм обновления сцены подключён
  к React-стейту: `ForceGraph` создаёт svg один раз на первых данных и дальше только вызывает
  `handle.update(data)` — в том числе на смену настроек (`nodeClones`), которая теперь тоже разбирается
  как добавление/удаление нод и связей, а не как пересборка сцены.

### Инкрементальное обновление сцены

- Сравнение изменений — **по значениям** (вариант A), а не по идентичности объекта: данные приезжают
  новым массивом на каждое обновление и могли быть изменены на месте. Снимок сравниваемых полей
  (`nodeRenderData`) снимается с прежних узлов **до** сборки новых, иначе правка уже отразится в
  «прежнем» состоянии и станет невидимой.
- Неизменённый узел переиспользуется тем же объектом: на него держатся предмет drag'а, данные
  отрисованной группы и концы связей. Изменённый узел обязан стать **новым** объектом: правка полей
  прежнего обнулила бы следующее сравнение, и повторная правка того же узла перестала бы замечаться
  (регрессия проверяется в Node — две правки подряд одного узла).
- Ключ связи направлен (`l:source>target`): `a→b` и `b→a` — разные связи, а переназначение конца —
  это exit старой связи и enter новой, не правка. Сравнение связей идёт по исходным
  `GraphLinkInput`, потому что в объекте связи `forceLink` уже подменила концы узлами и ключ
  прежней связи не восстановить.
- Связи при обновлении пересобираются новыми объектами: `forceLink.links()` заново разрешает
  строковые концы, а слой связей перерисовывает толщину по данным, так что переиспользование
  прежнего объекта связи ничего бы не сэкономило.
- Новый узел обязательно получает `x`/`y` **до** `simulation.nodes()`: при `undefined` d3 считает
  `isNaN(undefined) === false`, свою спираль не проставляет, и `NaN` расходится по всем силам.
  Точка высадки — вокруг центра масс уже известных соседей (`collectSeeds` + `seedPosition`),
  иначе узел «прилетает» из нуля карты; смещение ненулевое, потому что совпавшие координаты двух
  тел дают деление на ноль в силах.
- Порядок вызовов в `update()`: `simulation.nodes()` (проставляет `index`) → `linkForce.links()`
  (разрешает концы и пересчитывает `bias` по `index`) → `alpha(UPDATE_ALPHA).restart()`. Без
  `restart()` остывшая симуляция (stepper гаснет на `alphaMin`) не сдвинется, даже если `alpha` поднят.
- Смена `type` узла меняет его цвет, а значит и вид его связей: такие связи попадают в
  `changed.links` и перерисовываются, хотя их данные не менялись.
- Слой (`GraphLayer.sync(data, dirtyKeys)`) не трогает существующий DOM-элемент, если его ключ не в
  `dirtyKeys`, — только дописывает данные; для «грязных» элементов вызывается `renderer.update`.
  Если при этом и `renderKey` группы равен прежнему, раскладка облака и мерка текста не вызываются
  вовсе (страховка от перерисовки по чужой причине: смена типа у соседа помечает связь, а не узел).
  Снятый элемент очищается от `__data__`: иначе он держит объект симуляции, а тот через концы
  связей — весь прежний граф.
- Дубликаты id в новых данных схлопываются в первую запись (`diffNodes`, `diffLinks`), а связь с
  отсутствующим концом отбрасывается на разборе: второй узел с тем же id попал бы в
  `simulation.nodes()` дважды (d3 падает на `index`), а такая связь надорвала бы
  `linkForce.links()` — то есть обновление осталось бы с прежним набором связей.

## Как проверять изменения

Перед коммитом обязательно: `npm run lint` и `npm run check-types` — оба должны дать exit 0.
Вывод `tsc` цветной, при разборе через grep его надо чистить: `| sed -e 's/\x1b\[[0-9;]*m//g'`,
иначе ошибки «не находятся».

Логика без браузера (быстро, ловит NaN, нерезолвленные связи, утечку мутаций):

1. Написать скрипт и обязательно положить его **внутрь проекта** — из `/tmp` не резолвится `vite`.
2. Поднять Vite в SSR-режиме и загрузить модуль напрямую:

   ```js
   const server = await createServer({ root: process.cwd(), server: { middlewareMode: true }, appType: 'custom' })
   const mod = await server.ssrLoadModule('/src/components/ForceGraph/forceGraph.ts')
   ```

3. Проверить инварианты данных и симуляции: узлов и связей ровно столько, сколько в `graphData`; id
   уникальны, концы всех связей найдены; `link.source`/`link.target` после `createSimulation` —
   объекты-узлы, а не id; `prepareGraph` не портит `graphData` (сравнить `JSON.stringify` до и после);
   после долгого `tick` `alpha()` доходит до `alphaMin` — сравнивать с допуском, строгое равенство
   ловит хвост плавающей точки; нет нечисловых/`null` координат; `createTypeColors` даёт разным типам
   разные цвета; у работ `title` короткий и есть `description`, у патентов `description` отсутствует.
4. «Желе» мерить жестом в Node, а не на глаз: симуляцию сначала доводят `tick`-ами до `alphaMin` —
   раскладка раскрывается сотни тиков, и без этого в прокат попадёт она сама, а не жест. Потом берут
   один и тот же узел по id, ставят ему `fx`/`fy` и двигают по 8 единиц сцены за тик, держа
   `alphaTarget` как при drag, а после отпускания догоняют до `alphaMin`. Считать прокат остальных
   узлов (сумму смещений и максимум за один тик), остаточный сдвиг карты после жеста и нормировать
   его на пройденный узлом путь — иначе прогоны не сравнить. Отдельно и обязательно — геометрия покоя:
   медианный просвет связанной пары, просвет до ближайшего несвязанного соседа, число наездов тел и
   разлёт по сцене. От разогрева жеста равновесие не зависит (`alphaTarget` двигает только скорость
   сходимости), поэтому неизменная геометрия покоя — это и есть контроль, что ручка «желе» не сломала
   картинку.
5. Мерку текста в Node подменяем своей (`(text, size) => text.length * size * 0.55`): раскладка облаков
   от неё и считается. Проверить: `truncateToWidth` отдаёт префикс исходной строки с одним «…»,
   влезает в потолок, но не оставляет большой запас, короткую строку не трогает; `createCloudLayouts`
   даёт запись на каждый узел, облака с описанием выше, чем без, иконки квадратные, левый край текста
   сдвинут на паддинг (и ещё на `WARNING_GUTTER` при `hasWarning`), точка предупреждения внутри зоны
   паддинга; после растяжки раскладки соседи стоят заметно дальше, а наездов облаков — единицы.
6. Инварианты обновления данных (`forceGraphUpdate` + `crud/*`) проверяются так же в Node — план и
   состояние строятся без DOM: на идентичных данных пустой план, а неизменённый узел остаётся тем же
   объектом и сохраняет `x`/y; правка заголовка даёт `updatedNodes === ['a']` и ключ `n:a` в
   `changedNodeKeys`; **две правки подряд одного узла** замечаются обе (ловит регрессию с мутированным
   «прежним» снимком); у нового узла координаты конечны и не равны нулю, концы всех связей после
   `linkForce.links()` — объекты, `NaN` в `x`/`y` нет; при удалении узла уходят и его связи; связь в
   несуществующий узел и дубликат id отбрасываются на разборе, а не доходят до `forceLink`.
   Отдельно проверять, что `createTypeColors` держит оттенок типа между обновлениями и не
   перекрашивает прежние типы при появлении нового.
7. Удалить временный скрипт (он не должен попадать в коммит).

Проверка интерфейса — headless Chromium через Playwright (лежит в `devDependencies` проекта):

- Запускать с `LD_LIBRARY_PATH=/tmp/pwlibs/usr/lib/x86_64-linux-gnu`: браузер из кеша
  (`~/.cache/ms-playwright`) собран под другой дистрибутив, и libnspr4/libnss3/
  libasound2 к нему надо распаковывать из .deb руками (`apt-get download`, затем `dpkg-deb -x`) —
  без root. `chromium.launch()` в проекте берёт `chrome-headless-shell` из кеша сам.
- Дев на `http://127.0.0.1:5199/`, превью на `http://127.0.0.1:5198/`; проверять стоит на обоих.
- Данные d3 удобно читать из DOM: `el.__data__` на группе/линии.
- До жестов дождаться покоя карты: симуляция стартует с alpha 1 и раскрывается сотни тиков, так что
  снимок сразу после `waitForSelector` попадёт на разъезжающуюся раскладку, и любой прокат покажет
  ерунду. Ждать по координатам (две подряд спокойные выборки), а не по часам: alpha снаружи не видна.
- Проверка Node-инвариантов полезна и для цвета: у `tintToWhite` каждый канал строго светлее исходного,
  при `ratio 0` цвет не меняется, при `ratio 1` выходит белый.
- Узлы — группы, а не кружки: подписи ищутся как `group.querySelectorAll('text')`, тело — как
  `querySelector('rect')`, а `getBBox()` возвращает координаты внутри группы, то есть вокруг нуля,
  а не в пикселях сцены.
- Панораму и зум начинать внутри `svg`, но вне узлов (`document.elementFromPoint` +
  `closest('.force-graph__node')`), иначе жест перехватит drag узла (второй параметр `tick`-проверок:
  `transform` группы должен стать `translate(...) scale(...)` при нуле подвешенных узлов).
- Осторожно с привязкой к `null`: d3 оставляет `fx`/`fy` в `undefined`, сравнение с `null`
  строгим равенством даёт ложное «не сбросилось»; использовать `!= null`.
- Скриншот делать **до** жестов панорамы и зума: после них видна не сцена, а сдвинутый и увеличенный кадр.
- Чекбоксы панели настроек в разметке настоящие, но спрятаны (`opacity: 0`, 1px) под рисованным
  тогглом: `locator.check()` в Playwright на них падает («перехватывает pointer events»), поэтому
  кликать надо по `label` (`.settings-panel__option`), а клавиатуру проверять через
  `locator.press('Space')` на самом `input`.

## Грабли, которые уже стоили времени

- Эмуляция загрузки в `ForceGraph` держится на `setTimeout`: в `StrictMode` эффект выполняется дважды,
  но первый таймер снимается очисткой, поэтому данные приходят один раз — это норма (раньше на этом
  месте был `fetch`, который абортился и давал ложное «запрос упал» в консоли).
- `npm run lint` запускает prettier по всему проекту, поэтому новый файл в корне будет
  переформатирован; `.prettierignore` исключает `public`, `dist`, `.vscode`, логи и lock-файл.
- Браузерная проверка работает только там, где есть кеш Playwright и распакованные `.deb`-библиотеки
  (`~/.cache/ms-playwright`, `/tmp/pwlibs`). В свежем окружении их нет, и `chromium.launch()` падает
  на отсутствии исполняемого файла — это не поломка кода, и выдавать её за «проверено в браузере»
  нельзя: DOM-слой в таком случае остаётся непроверенным и это надо честно сказать в отчёте.
- `src/data/graph.ts` prettier сильно разворачивает: файл не стоит править вручную и не стоит пугаться
  его размера — лимит `max-lines` для `src/data` отключён.
- Исходные данные графа раздаются gzip-ом: если понадобится скачать их заново, `curl` без
  `--compressed` вернёт мусор.
- Порядок объявлений в модуле важен для линтера (см. конвенции), а разбивка по файлам — для
  лимита длины: при добавлении кода в `forceGraphView.ts` сначала искать, что вынести.
- Мерку текста нельзя тянуть в чистые модули: `createTextMeasurer` трогает `document`, поэтому он
  живёт в `forceGraphText.ts` и вызывается только из отрисовки, а `createCloudLayouts` принимает
  мерку параметром. Иначе пробник в Node упадёт на отсутствии `document`.
- Ширина текста на канве и в svg совпадает не до последнего пикселя (разные хинтинги), поэтому
  подписи могут «съесть» единицу-другую паддинга; за это отвечает тест `getBBox()` в браузере —
  он ловит выход текста за тело облака.

## Состояние и следующий шаг

Каркас страницы, граф с физикой, типизированные данные и переделанный вид узлов уже на месте; детали
правок — в истории коммитов, актуальные значения — в коде. Коротко, что изменилось по сути:

- Данные переехали из JSON в типизированный модуль `src/data/graph.ts` (импорт вместо `fetch`,
  загрузка осталась эмуляцией), типы — в `src/types/graph.ts`.
- Данные перепакованы в кластеры: патентов 112 вместо 236, связей 201 вместо 275, компоненты —
  11 пар «работа + патент» и 34 много-рабочих кластера не крупнее 8 узлов (было 83 компоненты, из них
  36 пар и 36 «звёзд» на одной работе). Работы, подписи и связи сохранённых компонент не менялись,
  нумерация патентов осталась с пропусками. Силы сцены и раскладка при этом не трогались.
- Вид узлов: вместо кружков — облака по размеру текста у работ и иконки у патентов,
  тела залиты светлым оттенком цвета типа, раскладка растянута, сетка фона удалена целиком.
- Влияние узлов друг на друга ослаблено по замеру: сила связи задана явно и слабо (`LINK_STRENGTH`),
  а разогрев симуляции на перетаскивании снижен вдвое (`DRAG_ALPHA_TARGET`). За жест в 320 единиц
  сцены прокат остальных узлов упал с 1788 до 879 единиц (пик за тик — 2.8 → 1.5), остаточный сдвиг
  карты после отпускания — с 17/99 до 9/64, при неизменной геометрии покоя. Заряд и дистанция связи
  не менялись: как показал замер, «желе» держится на разогреве жеста, а не на них.
- Настройки: панель в `aside` собирает их формой, `App` держит их в стейте и передаёт в `ForceGraph`.
  Реализовано `nodeClones` (клонирование графа в `useMemo` перед сборкой сцены) и семь числовых
  ручек физики (`layoutScale`, `linkDistance`, `linkStrength`, `chargeStrength`, `velocityDecay`,
  `dragAlphaTarget`, `updateAlpha`): они едут в `createForceGraph` как опции, а на смене —
  применяются к живой сцене через `setPhysics`, без пересборки svg. Значения по умолчанию панель
  берёт у констант сцены, так что «ничего не трогали» — это прежняя карта. `showFullSubNodes` и
  `hideSubNodes` пока только доезжают до `ForceGraph` и сцену не меняют; они ждут своей реализации
  в `forceGraphView`/раскладке. Сохранённые в localStorage настройки старой версии (без полей
  физики) отбрасываются целиком — так же, как и раньше, частичного разбора нет.
- Инкрементальное обновление данных — реализовано на уровне сцены: `createForceGraph()` возвращает
  `{ svg, update(data), destroy() }`, и `update` добавляет/обновляет/удаляет узлы и связи без
  пересборки svg; раскладка, панорама/зум и сама симуляция сохраняются. Логика разбора — чистая, в
  `forceGraphUpdate.ts`: сравнение по значениям узлов (`isNodeRenderDataChanged`), посев новых
  координат (`collectSeeds` + `seedPosition`), переиспользование неизменных объектов (на них держатся
  subject drag'а и концы связей). Изменённый узел обязательно становится новым объектом, иначе
  следующая правка того же узла остаётся невидимой (регрессия проверена в Node); новый узел всегда
  получает числовые `x`/`y` до `simulation.nodes()` (иначе `NaN` расходится по силам). Связи
  сравниваются как исходные `GraphLinkInput`, их концы после `linkForce.links()` — объекты; порядок
  вызовов в `update()` — `nodes()` → `links()` → `alpha().restart()`. Разбор лежит в
  `forceGraphUpdate.ts`, а CRUD отдельной сущности — в `crud/graphNodesCRUD.ts` и
  `crud/graphLinksCRUD.ts`; состояние сцены для сравнения читается из симуляции и силы связей
  (`readGraphState`), своего «прежнего графа» больше нет.
  Подключено к React-стейту: `ForceGraph` создаёт svg на первых данных и доставляет изменения через
  `handle.update(data)` — включая смену настроек, которая теперь тоже разбирается как CRUD, а не как
  пересборка сцены. Слой получает полный список сущностей плюс ключи изменённых (`dirtyKeys`),
  поэтому мерка текста и перерисовка группы идут только по правленным узлам.
  Проверено в Node: идентичные данные дают пустой план, правка заголовка сохраняет позицию и
  отмечает только этот узел, две подряд правки одного узла ловятся обе, у нового узла координаты
  конечны и не нулевые, `NaN` нет, связи удалённого узла уходят вместе с ним, цвет типа стабилен.
  **Браузерная проверка DOM-слоя в этом окружении не выполнялась** — нет кеша Playwright, так что
  `sync` слоёв, `renderKey`-пропуск перерисовки и сохранение панорамы при обновлении подтверждены
  только чтением кода.
- Следующее по виду: раскрытие иконки `subNode` (её `title`/`description` для этого и сохранены),
  группировка узлов в «кучки», подписи и иконки в экранных пикселях, а не в единицах сцены (сейчас они
  растут вместе с зумом).
- Обрезание подписей сейчас по ширине, без учёта числа строк: у описания всегда одна строка. Если
  понадобится многострочное облако, менять `createCloudLayout` (высота и центры строк уже считаются от
  блока строк, так что добавление строк — точечная правка).
- Доступность (клавиатура, не-нативные подсказки) — сознательно вне задачи: панорама и зум только
  мышью/трекпадом, подсказки узлов — нативные `<title>`.
